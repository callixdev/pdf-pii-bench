pdf-pii-bench is an open source corpus of realistic PDF documents for evaluating PII detection. It contains 50 documents across 8 categories, with 1,121 manually verified ground-truth text spans.

This work was inspired by the release of OpenAI's [privacy-filter](https://github.com/openai/privacy-filter) model, a big step forward in small PII detection models. The ground-truth text spans are labeled using the privacy-filter label schema.

This repository includes:

- The dataset of PDF files, extracted text, and ground-truth labels
- Baseline code to run the privacy-filter model on the data and report results
- A harness to run your own model on this dataset, using either the PDF files or the extracted text.



The documents in this benchmark are realistic versions of the sensitive documents that individuals and small businesses use every day: tax forms, bank statements, invoices, leases, etc. The real-world documents are often PDFs, with tables and forms providing extra challenges for redaction. Those challenges are replicated here.

This provides a testing ground for models and products that deal with sensitive personal data, in situations where real examples are not available because of data privacy concerns.

Community contributions are welcomed - see `CONTRIBUTING.md` for details.

## Dataset

The PDFs and PII spans in this benchmark were generated by LLMs (Claude Opus 4.8 and Fable 5), then manually verified. 

Dataset details:

| | |
|---|---|
| Documents | 50 PDFs, 8 categories |
| Ground truth | 1,121 char-offset spans |
| Labels | `private_person`, `private_email`, `private_phone`, `private_address`, `private_url`, `private_date`, `account_number`, `secret` |
| Subject tags | contact-info spans carry `person` \| `org` \| `agency` — who the channel reaches |
| Locale | US-only — US document types and US-format PII throughout |
| Text space | one canonical extraction per PDF (`data/text_data.json`) |
| License | dataset CC BY 4.0, code MIT (see `data/LICENSE` for the IRS public-domain carve-out) |

See `DATASET.md` for more details, including a guide to the annotation policy.

Ground truth is checked during CI to prevent errors. `data/ground_truth.json` is the
source of truth, and CI runs `src.validate` on every push. The validator checks the offsets 
(`text[start:end] == span.text`), that labels are within the allowed set, that each piece of 
contact info has a subject tag, and that repeat values are annotated.

Any corrections to the dataset should edit the ground truth directly 
and are batched into tagged releases (see `CONTRIBUTING.md`)

## Metrics and scoring

Precision, recall and F1 are reported on a per-label basis in two modes:

- **exact** — identical offsets and label.
- **overlap** — same label and (prediction contains the ground-truth
  span, or IoU ≥ 0.5). 

A third mode is also reported, termed the **redaction** mode. This is at the character level and is label-agnostic. Recall is the fraction of ground-truth PII characters covered by any prediction (a span caught under the wrong label is still redacted), precision the fraction of predicted characters that lie inside ground truth. Redaction recall measures what proportion of the characters in a PII span are identified by a model as PII, regardless of the label (or: "what fraction of the PII would actually be blacked out?). 

Scoring happens on the same ground truth, regardless of whether the system uses the pdf files or the extracted text version.

Systems are scored only on PII, not on organization contact info (tagged `org` and `agency` - see `DATASET.md` for more details). Org/agency spans don't count toward recall, and predictions covering them are charged no false positive. This means that detecting the IRS's printed hotline is neither rewarded nor punished.


## Running the privacy-filter model baseline

Run the baseline with:

```bash
uv run pytest                                             # harness self-check (no model)

uv run --extra baseline python -m src.run_privacy_filter  # opf on all 50 docs → results/privacy-filter.json
uv run python -m src.publish                              # regenerate RESULTS.md + README block
```

The core install has no dependencies beyond Python — scoring your own
predictions needs nothing else. The `baseline` extra pulls in the
reference model (`opf`, a pinned git dependency).

The baseline's per-document predictions are committed
(`results/cache/privacy-filter/`), so `run_privacy_filter` re-scores
instantly without touching the model — you can verify the published
numbers in seconds. To re-run inference from scratch, pass
`--no-cache`: the first run downloads the model checkpoint (~2.8 GB)
and takes ~25 minutes on CPU. Predictions are cached per document (`results/cache/<system>/`)
and written as each document finishes, so interrupted runs keep their
progress. Documents are immutable; the cache does **not** detect model
changes — pass `--no-cache` after changing a system.

## Evaluating your own system

Code is provided to evaluate both text->spans models and pdf->spans models: 

### Text in, spans out

Run your detector over the canonical text and score the predictions
directly:

```bash
uv run python -m src.score_predictions my_predictions.json
```

`my_predictions.json` maps doc id → spans into the canonical text of
`data/text_data.json`:

```json
{
  "bank_statement": [
    {"start": 120, "end": 136, "text": "Dana Whitfield", "label": "private_person"}
  ]
}
```

### PDF in, spans out (the adapter contract)

If your system owns its PDF extraction, wrap it in an adapter and the
harness will drive it:

```bash
uv run python -m src.harness --adapter "your-command-here"
```

The adapter is a subprocess speaking JSONL:

- **stdin**, one line per document: `{"id": "...", "pdf": "path/to.pdf"}`
- **stdout**, one line per input document:
  `{"id": "...", "text": "<full extracted text>", "spans": [{"start": 0, "end": 14, "text": "...", "label": "private_person"}]}`

Offsets must point into the *canonical* text: the harness byte-compares
the adapter's `text` against `data/text_data.json` and fails
on mismatch, so scores across systems are always in one text space. If
your extraction differs, either map your offsets to the canonical text
or use the text-in path above.


## Layout

```
data/
├── pdfs/                 ← the 50 PDF documents
├── text_data.json        ← canonical text per doc (with category)
├── ground_truth.json     ← char-offset spans into the canonical text
└── LICENSE               ← CC BY 4.0 + IRS carve-out + disclaimers
src/
├── dataset_utils.py      ← text/ground-truth loading
├── validate.py           ← ground-truth validator (the CI gate)
├── cache.py              ← per-document prediction cache
├── scorer.py             ← span matching, per-label and micro P/R/F1
├── run_privacy_filter.py ← privacy-filter (opf) baseline runner
├── harness.py            ← adapter runner (bring your own system)
├── score_predictions.py  ← score a predictions file directly
└── publish.py            ← generates RESULTS.md + the README block
results/
├── privacy-filter.json   ← committed baseline scores
└── cache/                ← per-document predictions (see src/cache.py)
tests/                    ← pytest suite (see tests/README.md)
DATASET.md                ← annotation policy: labels, subject tags, categories
RESULTS.md                ← full result tables (generated by src.publish)
CONTRIBUTING.md           ← corrections, new documents, release process
```

`RESULTS.md` and the README results block above are generated by
`src.publish` from `results/privacy-filter.json` — never edit them by
hand. CI re-checks them on every push (`src.publish --check`) along
with the test suite and the ground-truth validator, so the published
numbers cannot drift from the committed results.
